Definitions

What is a rollup?

Execute transactions off-chain, settle them on-chain.

Off-chain — the rollup operator

Executes many transactions against its own copy of the state. Fast, cheap, flexible — and by itself, completely untrusted.
⇄

On-chain — the contract

Escrows all deposited funds and stores one 32-byte state root — a Merkle commitment to every account. Advancing the root requires convincing the contract the transition was valid.
  • All rollup state — every account, every balance — is summarized by one number on chain.
  • Users enter via on-chain deposits and leave via on-chain withdrawals; the contract is the custodian, not the operator.
  • The whole design question: how does the contract know a proposed new root is honest?

Why now

Protocol 25/26 made this possible on Stellar

  • Protocol 25 "X-Ray" (Jan 2026) — native BN254 curve ops + pairing (CAP-0074) and Poseidon2 hashing (CAP-0075) as host functions: the exact primitives an UltraHonk verifier needs.
  • SLP-0004 (a week later) — a validator-voted limits upgrade (not a protocol release) raised per-tx CPU 100M → 400M instructions, motivated by the new ZK host functions.
  • Protocol 26 "Yardstick" (May 2026) — CAP-0080 added G1 multi-scalar multiplication, Fr field arithmetic, and curve-membership checks, cutting the Noir/UltraHonk verifier ~5×: 558M → 112M instructions (and the contract 130 KB → 15 KB). Before this, verification didn't fit even under the raised cap.
  • No precompile hacks, no custom protocol changes: the verifier is a normal Soroban contract (Nethermind's rs-soroban-ultrahonk).

Architecture

Three machines, one trust boundary — a payment's journey

  • Everything left of the trust boundary can lie, crash, or disappear — funds stay safe: only a valid proof can advance the root.
  • Batching is the whole business model: N payments amortize one ~fixed proof and one ~0.12 XLM Stellar transaction.
  • Deposits, withdrawals, and data availability ride the same loop — details on the next slides.
The ZK part

The state root, from the bottom up

  • Every account is a leaf: a rollup public key, a balance, a nonce, hashed together. Empty slots are 0.
  • Hash pairwise up 8 levels → one 32-byte root. That root is the only state the contract stores.
  • Any balance is provable with just 8 sibling hashes — the wallet checks its own balance against the on-chain root exactly this way: verify, never trust.
  • A payment touches two leaves (sender −amount, recipient +amount): recompute two paths → a new root. That recomputation is what the circuit does, payment after payment — next slide.
The ZK part

What the proof actually proves

  • State = a depth-8 Poseidon2 Merkle tree (256 accounts). Leaf = Poseidon2(DOMAIN, pk_x, balance, nonce).
  • Per payment, the circuit enforces: a valid Grumpkin Schnorr signature, balance ≥ amount (range-checked to 2⁶⁴), nonce increment, and two Merkle updates (sender, recipient) — ≈16.4K gates per payment.
  • Deposits and withdrawals are folded into running hashes the contract independently recomputes.
The contract never sees a single transaction. It sees five field elements and a proof that some valid set of signed transactions transforms old_root into new_root.

The ZK part

Why Poseidon and Grumpkin — not SHA-256 and Ed25519?

A circuit doesn't execute instructions — it checks equations over a prime field (BN254's scalar field, here). Crypto that's already field math is nearly free; crypto built for CPUs must be emulated bit by bit.

hash SHA-256 — tens of thousands of gates

  • Grumpkin's trick: its base field is BN254's scalar field (the two form a cycle) — so curve arithmetic inside the circuit is just ordinary field math, no emulation.
  • Same math on both sides: CAP-0075 makes Poseidon2 a Soroban host function, so the contract recomputes the very same hashes cheaply on-chain.
  • Ed25519 doesn't disappear: it still guards your Stellar account and signs deposits. The Grumpkin key is a rollup-only signing key held by the wallet.
Trust model

The operator is trusted for liveness,
never for correctness.

What the sequencer cannot do

Steal funds, forge balances, skip deposits, redirect withdrawals, or advance the root with an invalid transition — every root move is proven, and the contract checks the proof against its own bookkeeping.

What the sequencer can do

Go offline or withhold a batch's data blob. Users then can't compute Merkle paths for newer roots — the system freezes. That's the validium bargain, and it sets up the data-availability discussion in a moment.

Production hardening path: DAC signatures over da_commitment verified in submit_batch, plus a forced-exit escape hatch. Neither exists in the prototype.

UltraHonk via bb 0.87, Apple M5 Pro (18 cores), measured 2026-07-07. Proving scales ~linearly with gates; verification doesn't care.

  • The cadence rule: proving must beat block time (~5s on Stellar). Laptop: n128 → ~26 tx/s; 2-core cloud VM: n4 → 0.8 tx/s.
  • Vertical scaling: get a bigger machine — M4 Pro → M5 Pro alone: 1.4–1.8× faster.
  • Bigger batches: fees don't grow with batch size — trade latency for throughput, zero infra.
  • Prover farm + recursion: loses on one machine, wins across many — 4 workers × n256 + an aggregator ≈ ~128 tx/s.
These numbers are UltraHonk, which we chose for simplicity — proof systems built for scale (like Lighter's Plonky2) prove far faster, and production rollups add GPUs and prover farms on top.
Scalability · 2 of 3

On-chain costs don't grow with the batch

  • CPU never binds: verification grows ~+2M instructions per circuit doubling. Even a 2²⁴-gate circuit (~1,000+ payments) verifies at ~103M of the 400M cap.
  • Bytes are constant: submit_batch is ~15 KB — 14.6 KB of it the proof — whether the batch holds 4 payments or 4,096. Just 11% of the 132,096 B tx cap; the tx data itself lives off-chain (next slide).
  • Fees are flat: ~0.12 XLM per batch regardless of batch size — so cost per payment is 0.12/N, and the chain never caps batch size; the prover does.

Scalability · 3 of 3

Data availability: the real design choice

Proofs guarantee the root is correct — but to know your own balance (or exit without the operator), you need the underlying data. Where it lives is the scalability–trust dial:

On-chain data (rollup)

Calldata, then blobs (EIP-4844) on Ethereum — Lighter posts ~65 MiB/day. Trustless reconstruction, but on-chain bytes cap your throughput and dominate cost.

Data-availability committee

A quorum signs that it holds the data; the contract checks signatures. Middle ground — trust k-of-n instead of one operator.

Off-chain (validium — Soribium)

Only the proven da_commitment goes on chain. The blob is served at GET /da/:batch_num; anyone can re-fold it and check the commitment. Withholding freezes — never steals.
  • Soribium chose validium deliberately: payments DA is tiny (~28 B/payment), but Stellar has no blob space — full on-chain DA would burn the same byte budget that carries the proof.
  • The hardening ladder is incremental: single operator → DAC signatures in submit_batch → forced-exit escape hatch. Validity proofs stay identical the whole way.
Wrap-up

Takeaways

  • Validity is a solved primitive on Stellar today. Protocol 25/26 host functions verify UltraHonk natively at ~23% of the CPU budget — no protocol changes needed.
  • The prover is the bottleneck, not the chain. Scaling a zk-rollup is a provisioning problem: hardware, farms, recursion — all measured, all public.
  • The value is throughput and new features, not fees. On-chain cost per batch is flat, so throughput scales with the prover, not the chain — plus a substrate for privacy and custom execution.
